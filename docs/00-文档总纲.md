# 00 - 文档总纲

本文档规定 `docs/` 与根文档的分类法、内容归属和命名规则，是文档体系的元文档。
它约束的是「文档怎么写」，不含任何游戏内容与实现细节。工程纪律见 `AGENTS.md`。

## 1. 目的与适用范围

`AGENTS.md` 第 5、7、8 条要求文档保持最新、同一内容只存在一处、过程性内容不入 `docs/`。
这三条在没有归属规则时无法执行：项目结构树与模块表此前散在 README（两份）、白皮书（两份）、
`AGENTS.md` 共五处，已产生实测腐化（白皮书记「6 个音效」，`assets/sounds/` 实际 5 个 OGG；
白皮书与 `CLAUDE.md` 旧稿对 `GameSceneRenderer` 分别记 525 行与 446 行）。本文把这些要求
落成可判定的规则。

适用范围：`docs/` 全部文件、根目录 `README.md`、`AGENTS.md`、`CHANGELOG.md`、`VERSION`。

## 3. 唯一归属矩阵

每类事实只有一个权威位置。其他位置只允许引用，**不允许复制内容**。

| 事实类型 | 权威位置 | 其他文档允许的形态 |
|---|---|---|
| 版本号 | `VERSION` | 文字引用 `v2.6.0`，须与 `VERSION` 一致 |
| 构建与运行命令 | `AGENTS.md` | README 摘常用命令，不展开参数 |
| 工程纪律 | `AGENTS.md` | 其他文档只引用条款编号 |
| 模块与项目结构树 | `10-架构设计.md` | 引用章节，禁止再画一份树 |
| 技术栈与版本 | `10-架构设计.md` | 引用 |
| 游戏内容数值（地图/塔/敌人/子弹/成就/奖励/存档槽/资源数） | `01-白皮书.md` | 引用 |
| 需求条目 | `03-需求文档.md`（`F-xxx` / `NF-xxx`） | 引用编号 |
| 已知缺口 | `03-需求文档.md` 附录（`GAP-xx`） | 引用 `GAP-xx` 编号 |
| 版本边界（做什么/不做什么） | `02-版本边界与路线图.md` | 引用版本小节 |
| 平台服务与存档契约 | `12-接口设计.md` | 引用 |
| 算法与子系统实现 | `11-详细方案设计.md` | 引用 |
| 已发布版本的变更记录 | `CHANGELOG.md` | 引用版本小节 |

## 4. 交叉引用规范

- 形式为「路径 + 章节名」：`docs/10-架构设计.md §2 模块设计`。
- **禁止用行号定位代码**。行号随任意改动失效，实测已发生：`41-APK差距分析报告.md`
  记 `TowerData.java:615-625`，而 `sellValue()` 实际在第 460 行。需要指位时写符号名
  （`TowerData.sellValue()`）。
- 唯一例外：核查类快照文档（`3x`/`4x`）记录取证证据时保留 `文件路径:行号`。该次取证是
  冻结的历史事实，允许与活文档不同；但活文档描述现状一律用符号名（见 INV-02 限定语）。
- 文档间引用一律使用仓库相对路径，不使用 `../`、不使用绝对路径、不使用站点链接。
- 快照文档不修订：结论过期时在新文档中指向订正处，原文不改。迁移时为快照补元信息属于
  登记行为，不算修订结论。

## 5. 文档元信息规范

每份文档首部必须有 YAML frontmatter，字段如下：

| 字段 | 必填范围 | 含义 |
|---|---|---|
| `类型` | 全部 | `活文档` \| `快照` \| `归档` \| `过程`（SDD 计划与评审记录，实施完成后转归档或删除） |
| `文档版本` | 活文档 | 实质结论变更时 +0.1，并在文末「变更」行注明依据 |
| `权威范围` | 活文档 | 本文在 §3 矩阵中持有的事实类型，数组 |
| `对应版本` | 活文档 | 最后一次对齐的版本号 |
| `最后核对日期` | 活文档 | 与代码逐项核对的日期 |
| `冻结日期` | 快照 | 结论定稿日期 |
| `结论去向` | 快照 | 结论后续被哪个版本实施，或「仍有效」 |
| `归档原因` | 归档 | 为何退出主线 |
| `取代文档` | 归档 | 现在由哪份文档承载同类内容 |

`最后核对日期` 是时效判定的依据（INV-05）。

## 6. 命名与编号规则

- 文件夹名与文件名一律中文，加两位数字前缀（`50-对外文章/` 内的文件按发布日期命名例外）。
- 新增文档取所属段内下一个未使用号；**不重排已有号，删档不回收号**。
  重排会同时打断 git 历史与既有引用，回收号会让旧引用指向错误文档。
- 截图放 `docs/images/`，文件名用界面中文名。
- `80-实施计划/` 内文件用 `YYYY-MM-DD-主题.md` 命名，理由同上（按时间排列）。

## 7. 版本边界与一致性

`02-版本边界与路线图.md` 固定三段：§1 版本序列总表、§2 当前版本边界（本版做／本版不做／
完成判据）、§3 本版不收的缺口（只引用 `GAP-xx`）。

版本号一致性以 `VERSION` 为唯一真源，要求 `02 §1` 当前行、`CHANGELOG.md` 最新小节标题、
git tag 与之相等（INV-06）。

打包节点的固定顺序：`02` 定边界 → 冻结实现 → 改 `VERSION` → 写 `CHANGELOG` → 打 tag，
tag 说明文字取自 `02 §2` 的边界一句话。

已知历史欠账：`v2.5.0` 无对应 tag，在 `02 §1` 中登记为「已发布，缺 tag」，不追溯补打。

## 8. 能力声称与缺陷登记

文档里出现「自动」「支持」「已实现」「便于」这类承诺时，只写「代码里有这段逻辑」不算实现。
判定标准是端到端数据流四段：

| 段 | 要回答的问题 |
|---|---|
| 写入 | 谁产生、何时产生、写到哪里 |
| 存储 | 是否真的持久化、是否带关联键可定位归属 |
| 读取 | 谁读出来、该读取方是否在业务链路上 |
| 消费 | 读出的值是否进入用户可见的返回值、界面或决策 |

任一段断链即未实现。常见断链形态：只写不读、写入即丢弃、写路径通而读路径未接、静默兜底
掩盖失败、有能力无消费者、表述超出实际。

据此，`01-白皮书.md` 的能力矩阵固定三列：**能力 ｜ 设计意图 ｜ 实际生效**，第三列取值
✅（端到端可用）／⚠️（部分生效或有未覆盖依赖）／❌（代码存在但无效果）。
不允许用愿景口号描述现状；产品不具备的能力要显式写「不具备……能力」并说明架构原因。

**缺陷编号唯一**：全仓库只有一套缺陷编号 `GAP-xx`，登记在 `03-需求文档.md` 附录，
其他文档一律引用编号不自造清单（本次修订前的错误做法：`GAP-01` 只存在于
`11-详细方案设计.md` 第 9.3 节）。缺陷与「固有设计上限」必须区分：上限不是 bug，
标注清楚，否则后人会去「修」。

核查结论对外发布前须做严重度复核：判为「未实现」的要反向再搜一次是否有其他实现路径承担
该能力；判为严重的要确认坏结果实际能否发生。若复核后结论反转，公开说明是自己修正，不改口
掩盖。

## 9. 防腐化不变量

每条都可机械判定。校验器的输入限定为：`docs/**` 下 Markdown、根目录四份文档、git tag、
`assets/` 目录计数。

| 编号 | 规则 | 判定方式 |
|---|---|---|
| INV-01 | 引用有效 | 引用的 `docs/xxx.md` 路径存在；`§章节名` 能在目标文档标题行中找到 |
| INV-02 | 禁止行号定位代码 | 正则拦 `[A-Za-z0-9_]+\.java:\d+`，命中即要求改符号名；`3x`/`4x` 核查快照豁免（§4 例外） |
| INV-03 | 元信息齐全 | 按 §5 的必填矩阵逐字段校验 |
| INV-04 | 编号合规 | 文件与目录名匹配 `^\d{2}-`；段内号不重复 |
| INV-05 | 核对时效 | 活文档 `最后核对日期` 距今超过 90 天则告警 |
| INV-06 | 版本号一致 | `VERSION` == `02 §1` 当前行 == `CHANGELOG` 最新小节；tag 缺失降级为告警 |
| INV-07 | 声明数值与实际一致 | `01-白皮书` 的资源与内容计数与 `assets/` 实际计数逐项比对 |
| INV-08 | 禁流水账 | 正则拦「共 N 次提交」「N 行」「-N%」出现在 `0x`/`1x` 活文档；`90-历史归档` 与 `CHANGELOG.md` 豁免 |
| INV-09 | 能力声称带生效标注 | `01-白皮书` 能力矩阵每行第三列非空，取值限于 ✅/⚠️/❌；标 ⚠️/❌ 者必须在 `03` 附录有对应 `GAP-xx` |
| INV-10 | 缺陷编号唯一一致 | `GAP-xx` 只在 `03` 附录定义一次；全仓库引用的编号都能在附录找到；附录编号连续无跳号、无重复 |
| INV-11 | 结构完整无占位 | 每份文档代码围栏数量为偶数；无 `TODO:`、`TBD`、「待补充」与省略号缩写残留。本文与 `80-实施计划/` 豁免（§9 与 §11 是规则定义处，必然含这些字面量；计划正文也必然引用 `TODO`、「待补充」等字面量作为反例） |

### 刻意不做的检查

**跨文档语义重复检测**。误报率高、实现代价大，且本次迁移完成后重复已消除，后续靠 §3
矩阵人工守。不放一条长期告警、最终被人忽略的规则。

### 责任划分

本文只定义规则。校验器实现属于配套工具集，见 issue #3 的 `tools/` 之 `rd docs` 子命令。
规则与校验器必须同源：新增或删改 INV 只能改本文，校验器跟随，不允许校验器自带私规。

迁移完成前，本文对尚不存在的新路径（如 `docs/10-架构设计.md`）的引用属于计划态，
INV-01 自迁移完成起生效。
