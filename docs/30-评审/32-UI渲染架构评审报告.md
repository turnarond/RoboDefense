# 08 - UI 渲染架构评审报告（报告二：工程层）

- 日期：2026-07-19
- 设计依据：`docs/10-架构设计.md`、`docs/11-详细方案设计.md`（渲染与性能章节）
- 方法：3 个只读分析代理并行 + 主线程复核
- 分级：P0 阻塞性能或严重影响可维护性 / P1 明确改善 / P2 值得但非紧急 / P3 设计选择

## 一、渲染管线诊断

### 1.1 begin/end 碎片化（当前 10-19 对/帧 → 目标 2 对）

**常规游戏帧：10 对 begin/end**：

| # | 绘制步骤 | 位置 |
|---|---------|------|
| 1 | drawBackground（地图+星空） | `GamePlayScreen.java:382-393` |
| 2 | drawTowers（底座+转头） | `GamePlayScreen.java:406-431` |
| 3 | drawEnemies（精灵+血条） | `GamePlayScreen.java:441-487` |
| 4 | drawBullets（精灵/矩形） | `GamePlayScreen.java:497-522` |
| 5 | drawEnemyDefeatedEvents（飘字） | `GamePlayScreen.java:901-929` |
| 6 | drawHud（顶栏+底栏） | `GamePlayScreen.java:531-629` |
| 7 | renderTowerButtons | `UiRenderer.java:68-113` |
| 8 | renderControlButtons | `UiRenderer.java:236-252` |
| 9 | renderScaleSlider（选项6启用时） | `UiRenderer.java:296-303` |
| 10 | drawTowerButtonSprites | `GamePlayScreen.java:817-850` |

条件追加可达 **19 对**（升级对话框 + 暂停菜单 + 覆盖层全部触发时）。

**合并方案**：全部世界坐标步骤（1-5）共享同一相机变换 → 合并为 1 对。全部屏幕坐标步骤（6-10 + 全部 UiRenderer 方法 + 覆盖层）→ 合并为 1 对。**最终 2 对，消除 8+ 次 batch 提交。** ~30 行代码改动。

**级别：P0**。收益直接且风险低。

### 1.2 真正的瓶颈：drawRect() GPU flush

`LibGdxRenderer.drawRect()` 的实现是：
```
batch.end() → shapeRenderer.begin → rect → shapeRenderer.end → batch.begin()
```
**每个 drawRect 调用隐式执行一次 GPU flush。** 单帧统计：
- HUD 顶栏/底栏：7 次 drawRect → 7 次 flush
- 敌人血条（10 个半血敌人）：~20 次 drawRect → 20 次 flush
- 塔按钮面板：3-12 次 drawRect → 3-12 次 flush
- **单帧合计 20-40 次 GPU flush**

**级别：P0**。这是渲染帧率不稳的根本原因——消除不必要的 drawRect 比合并 begin/end 收益更大。

### 1.3 GameWorldRenderer 死代码

`GameWorldRenderer.render()` 是为单批次 Y-sort 渲染设计的，但：
- GamePlayScreen **不实现** GameWorld 接口（`implements GameWorld` 全局搜索零结果）
- 复活需新增 5 个接口方法 + 3-4 个 Adapter 类，~200-300 行
- 当前 inline 渲染（applyCameraTransform + 世界坐标直绘）更接近原版逻辑

**级别：P3**。不推荐复活——删除此死代码或保留作未来参考。

### 1.4 空间裁剪

CameraManager 可计算视锥体（需新增 4 个 getter，~4 行，零风险）。

但桌面端默认 zoom 全地图可见，裁剪无收益。仅在最大 zoom 时约 24% 对象在屏幕外。**桌面收益有限，但对 Android 小屏移植有价值。**

**级别：P2**——先加 getter 作为基础设施，裁剪逻辑按需启用。

### 1.5 脏标记优化

| 内容 | 帧间不变 | 可缓存 | 潜在节省 |
|------|---------|-------|---------|
| 地图背景 | 是 | FBO 缓存 | 消除整个 drawBackground |
| HUD 矩形 | 是（5 个 drawRect） | FBO 缓存 | 消除 5 次 flush |
| 塔按钮背景 | 仅金钱变/选中切换时变 | 脏标记 | 消除 3-12 次 flush |
| 塔底座/转头/敌人/子弹/飘字 | 否 | 不能脏 | — |

**最高性价比：塔按钮脏标记（~5 行代码）**——当 `money == lastMoney && activeTowerId == lastActiveTowerId` 时跳过整个 renderTowerButtons。

**级别：P1**（塔按钮）/ P2（HUD 缓存）/ P3（地图 FBO）。

## 二、代码组织审查

### 2.1 GamePlayScreen 拆解

| 职责区域 | 估算行数 | 占比 |
|---------|---------|------|
| 渲染代码（9 个 draw* 方法） | ~573 | 61.5% |
| 状态管理与游戏逻辑 | ~180 | 19% |
| 框架样板 | ~116 | 12.5% |
| 输入处理 | ~46 | 5% |
| 工具方法 | ~14 | 1.5% |
| 游戏循环 | ~2 | 0.2% |

**渲染代码占 61.5%——这是单体类膨胀的主因。** 拆解方案：
1. **提取 GameSceneRenderer**：接管全部 draw* 方法 + HUD 动画数字（displayMoney/Score/Health），~550 行
2. **提取 GameInputController**：接管 ESC/SPACE/F9 按键处理 + 暂停菜单点击，~100 行
3. **GamePlayScreen 保留**：协调角色（init/生命周期/runState 切换/游戏循环集成），~200 行

**级别：P1**。不阻塞但可维护性严重受损。

### 2.2 UiRenderer 职责混乱

- `renderActiveTowerPreview`（UiRenderer.java 旧版实现）——**零调用者死代码**。GamePlayScreen 自行实现了 drawActiveTowerPreview。
- `renderShortMessage` + `showShortMessage`——已有 `GameScreen.renderShortMessage()`（基类 125 行）实现了同样功能 + 计时。**三处重复**（GameScreen 基类 / UiRenderer / GamePlayScreen.showShortMessage）。
- UiRenderer 名不副实——612 行仅被 GamePlayScreen 使用，其他 8 个 Screen 无共享。

**级别：P1**。清理死代码并纠正命名/职责。

### 2.3 其他架构问题

- `LibGdxRenderer` 强制转型：`drawTowers()` 中 `(LibGdxRenderer) renderer` 破坏接口抽象——`applyCameraTransform` 不在 `GameRenderer` 接口中
- `formatWithCommas` 放在 GamePlayScreen 中——应为静态工具方法或在 GameScreen 基类
- 短消息三处实现——GameScreen 基类的 `shortMessage+shortMessageTimer` vs UiRenderer 的 `shortMessage+shortMessageTimer` vs GamePlayScreen 的同名方法

## 三、组件复用机会

### 3.1 标题栏（7 Screen，25 行重复代码）

7 个 Screen 的标题栏是**逐字复制粘贴**——仅标题文字和渲染器变量名不同。提取到 `GameScreen` 基类：
```java
protected void drawTitleBar(String title) {
    int sh = Gdx.graphics.getHeight(); int sw = Gdx.graphics.getWidth();
    GameRenderer r = game.getServices().getRenderer();
    r.drawRect(0, sh - 34, sw, 34, 0.06f, 0.08f, 0.16f, 0.93f);
    r.drawRect(0, sh - 1, sw, 2, 0.2f, 0.36f, 0.55f, 0.85f);
    r.drawText(title, 16, sh - 20, 0.75f, 0.85f, 0.95f, 1.0f);
}
```
**节省 25 行，消除 7 处硬编码颜色值。** 级别：P1。

### 3.2 返回按钮（6 Screen，~40 行重复）

6 个 Screen 的返回按钮代码高度一致——仅在位置（右上 vs 左下）、尺寸（100x34 到 140x45）、色系（标准蓝 vs 偏离）有差异。提取后每个 Screen 从 4-6 行减为 1 行调用。

**级别：P2**——报告一已在实现层面统一了色系，进一步提取收益较小。

### 3.3 面板（5 Screen）

半透明面板 + 蓝色装饰顶线的模式在 5 个 Screen 中出现。但各面板的尺寸差异大（从 CreditsScreen 的 420x260 到 GamePlayScreen 的 180x200）。参数化后统一为：
```java
protected void drawPanel(int x, int y, int w, int h, float alpha) { ... }
```
**级别：P2**。

### 3.4 列表/滚动（3 Screen）

Achievement/Reward/GameSave 三个列表界面各自实现了行高常量、滚动偏移量、键盘/鼠标滚动处理、滚动条绘制。代码相似度高但不完全一致。

**建议**：先提取 TitleBar/BackButton/Panel（纯复制粘贴），再评估 ScrollableList 提取（需接口设计）。

### 3.5 提取优先级

| 排名 | 组件 | 重复行数 | 出现次数 | 节省行数 | 风险 |
|------|------|---------|---------|---------|------|
| 1 | 标题栏 | 3-5 | 7 | 25 | 极低 |
| 2 | 返回按钮 | 4-6 | 6 | ~40 | 低 |
| 3 | 面板 | 3-5 | 5 | ~20 | 极低 |
| 4 | 列表/滚动 | 40-80 | 3 | ~120 | 中 |

## 四、分级结论

### P0 — 阻塞性能/维护性（3 项）

| # | 项 | 影响 |
|---|----|------|
| P0-1 | drawRect() 每次调用 GPU flush（20-40 次/帧） | 帧率不稳的最可能根源 |
| P0-2 | begin/end 碎片化 10-19 对（可并到 2 对） | 消除 8+ 次 batch 提交 |
| P0-3 | GamePlayScreen 61.5% 渲染代码（573/931 行） | 单体类膨胀——拆解提渲染器是重构入口 |

### P1 — 明确改善（5 项）

- 塔按钮脏标记（~5 行，最高性价比优化）
- UiRenderer 死代码清理（renderActiveTowerPreview + 短消息三处重复）
- 标题栏提取（7 Screen 绝对一致 → GameScreen 基类）
- LibGdxRenderer 强制转型消除（applyCameraTransform 入接口）
- formatWithCommas 位置（从 GamePlayScreen 升到 GameScreen 基类或工具类）

### P2 — 值得但非紧急（4 项）

- 返回按钮提取
- 面板统一组件
- HUD FBO 缓存
- CameraManager 视锥 getter

### P3 — 设计选择或低收益（3 项）

- GameWorldRenderer 复活（死代码清理或保留）
- 空间裁剪（桌面收益极小，Android 移植时有价值）
- 地图背景 FBO 缓存

## 五、重构路线图

分三阶段推进，每阶段有独立可交付物：

### 阶段 1：低风险清理（1-2 小时）

1. 标题栏提取到 `GameScreen.drawTitleBar(title)` → 7 Screen 替换
2. 返回按钮统一组件 → 6 Screen 替换
3. 删除 UiRenderer 死代码（renderActiveTowerPreview）+ 三处短消息统一
4. formatWithCommas 升到 GameScreen 基类

**可交付物**：8 个 Screen 各减少 3-8 行，消除 17 处硬编码颜色值，统一标题栏/返回按钮样式。

### 阶段 2：架构调整（2-3 小时）

5. 提取 `GameSceneRenderer`——接管 GamePlayScreen 的全部 draw* 方法
6. 提取 `GameInputController`——接管 ESC/SPACE/F9 处理
7. applyCameraTransform 信息入 `GameRenderer` 接口，消除强制转型
8. GamePlayScreen 缩减到 ~200 行协调角色

**可交付物**：GamePlayScreen 从 931 行降到 ~200 行，渲染逻辑独立可测试。

### 阶段 3：管线优化（1-2 小时）

9. 合并 begin/end 到 2 对（世界坐标 1 对 + 屏幕坐标 1 对）
10. 塔按钮脏标记（消除 3-12 次 drawRect flush/帧）
11. CameraManager 视锥 getter（为空间裁剪铺路）

**可交付物**：渲染帧率稳定，drawRect flush 减少 15-60%。
