# UI 评审与重构设计（视觉/体验 + 渲染/架构）

- 日期：2026-07-18
- 状态：已批准（brainstorming 会话中逐项确认）
- 基准：原版 Android APK Build 2900（9 Activity + 11 UI 组件类）vs 当前桌面版（9 Screen + 7 Renderer）

## 1. 目标与范围

在 APK 保真修复（计划①〜④）完成后，对界面显示功能进行**全量四维评审**：
设计一致性、交互可用性、渲染性能、代码架构。产出两份独立报告，每份附带分级结论与设计建议。

| 决策点 | 结论 |
|--------|------|
| 评审维度 | 全部四维（设计/交互/性能/架构） |
| 评审广度 | 全量（9 Screen + 7 Renderer + 渲染管线） |
| 分析方法 | 双报告分维（报告一：视觉/体验 → 报告二：工程层） |
| 产出形式 | 评审报告 + 重构设计 + 实施计划 |

## 2. 报告一：设计一致性与交互可用性

**产出文件**：`docs/07-UI设计交互评审报告.md`

### 2.1 共性审查

对 9 Screen 横向比较：
- 色彩体系一致性（背景色、文字色、辅助色的使用规律）
- 间距规范统一性（标题栏高度、按钮尺寸、行间距、边距）
- 字体大小统一性（标题/正文/辅助文字是否有尺寸层级）
- UI 模式遵循率（标题栏、面板、按钮的 drawRect 实现是否一致）

参考原版 Android XML 布局的组件使用方式（Button、CheckBox、TableLayout 等），识别两种体系差异。

### 2.2 逐界面审查

每个 Screen 的审查维度：
- 布局合理性：信息密度、视觉层级、空白利用
- 热区大小与间距：是否符合桌面鼠标操作标准（≥24px 点击目标）
- 键盘/鼠标双模适配：所有键盘快捷键是否有视觉提示、鼠标悬停是否有反馈
- 状态反馈完整度：按钮按下态、禁用态、选中态是否均有视觉区分
- 对应的原版 Activity 交互模式对比

### 2.3 交互模式差距

按交互类型归类（不分界面）：
- 拖拽放置（原版触屏 DragDrop → 桌面点击选择）
- 手势缩放（原版双指 Pinch → 桌面滚轮 + 滑块）
- 弹出/关闭行为（升级对话框、暂停菜单、确认框的开闭逻辑）
- 滚动/翻页（列表界面、地图切换的交互一致性）

### 2.4 分级结论

- P0：体验严重受损（关键操作无反馈、热区过小无法命中）
- P1：明显毛糙（各界面表现不一致、缺少必要的视觉提示）
- P2：可优化（不符合桌面软件习惯但功能可用）
- P3：风格选择差异（科幻主题 vs 原版 Android 风格的有意差异）
- 每条附双边证据或设计说明

### 2.5 设计建议

- 布局常量统一方案（标题栏高度、按钮标准尺寸、间距规范）
- 组件提取候选（供报告二细化）

## 3. 报告二：渲染性能与代码架构

**产出文件**：`docs/08-UI渲染架构评审报告.md`

### 3.1 渲染管线诊断

- begin/end 碎片化：当前 16-20 对/帧 → 目标 2-3 对/帧
- GameWorldRenderer 死代码复活：单批次 Y-sort 渲染 vs 当前三遍独立遍历
- 空间裁剪可行性：视锥体外的塔/敌人/子弹是否可跳过
- 脏标记优化：纯 UI 层（标题栏/按钮等静态内容）是否可缓存
- Camera transform 重复设置：各步骤独立设置 → 统一设置一次

### 3.2 代码组织审查

- GamePlayScreen 单体拆解（893 行，承担渲染/输入/状态机/游戏循环四重职责）
- UiRenderer 职责边界（612 行但仅被 GamePlayScreen 使用）
- 8 个非游戏 Screen 的共享组件缺失

### 3.3 组件复用机会

按出现频率排序：
- 标题栏（9 Screen 均独立实现相同模式）
- 面板（半透明矩形 + 蓝色顶线，6 处重复）
- 按钮（drawRect 模拟，全部 Screen 均有）
- 列表/滚动（Achievement/Reward/GameSave 三处独立实现）
- 状态机模式（暂停菜单、升级对话框、确认框的 open/close 逻辑相似）

### 3.4 分级结论

- P0：阻塞性能（帧率不稳、GPU flush 过多导致移动端不可用）
- P1：架构债（单体类过大、重复代码超过 30 行）
- P2：可优化（有重复但量小、暂时不影响开发效率）
- P3：设计选择（有意保持的简单实现）

### 3.5 重构路线图

阶段化推进，每阶段有独立可交付物：
1. **组件提取**（低风险）：标题栏/面板/按钮 → UiRenderer → 8 Screen 逐步替换
2. **GamePlayScreen 拆分**（中风险）：分离渲染/输入/状态，引入 GameWorldRenderer
3. **管线优化**（需要阶段 2 完成）：begin/end 合并、空间裁剪、脏标记

## 4. 执行方法

两份报告均采用相同的执行流程：
1. 派 4-6 个只读代理对指定 Screen/组件进行深度分析
2. 主线程复核全部 P0/P1 项（原版 ↔ 当前双边源码）
3. 撰写报告 → 自审 → 用户审阅
4. 对 P0/P1 项调用 writing-plans 编写实施计划

## 5. 成功标准

- 两份报告覆盖全部 9 Screen + 7 Renderer + 渲染管线
- 每条 P0/P1 附双边证据或代码位置
- 重构路线图有明确的阶段划分和阶段间依赖
- 为后续实施计划提供可直接派发的任务清单
